# daemon 操作管理

## 责任边界

CLI／TUI 负责收集输入、提交结构化请求和显示状态；daemon 负责记录操作、调度工作流、
保存结果和恢复未完成操作。监管进程仅负责 daemon 的退避拉起，不解释业务事务。
业务操作的记录与业务事务分别管理：操作记录回答“用户的请求执行到哪里”，事务记录
回答“安装现场如何安全提交或恢复”。daemon 存活不等于某个操作已经成功。

`install`、`reinit`、`migrate`、`uninstall`、`restore`、`switch`、网络确认／手工回滚和
三类 `repair` 由 daemon 直接调用工作流。`update` 在前端解析和确认后提交 `switch`。
操作共用串行调度和安装锁，业务执行不启动另一个 lkit 进程。外部服务管理工具是
独立进程；`self install/upgrade/remove` 直接执行。

前端通过存活 PID 与对应能力标记判断 daemon 是否可接收操作，不要求 daemon 的
可执行文件路径仍可用于启动子进程。请求不传递终端、原始参数、工作目录或会话环境。

## 操作状态

| 状态 | 含义 |
|---|---|
| `queued` | 请求已持久化，尚未开始修改现场 |
| `running` | daemon 已领取并开始处理 |
| `awaiting_confirmation` | 配置已激活，等待显式网络确认，尚未提交 |
| `recovering` | 关联事务未终结，继续按事务规则恢复 |
| `succeeded` | 工作流成功；修改事务已提交，网络回滚事务已回滚 |
| `failed` | 执行失败；关联事务已经回滚或失败 |
| `interrupted` | daemon 中断且没有足够依据确定结果，不自动重放请求 |
| `cancelled` | 排队请求已取消，或下载取消已完成清理且没有修改活动安装 |

终态不可重新领取。请求使用独立操作 ID，工作流在创建事务之前持久化操作与事务的
关联。CLI 提交后输出操作 ID；前端断开不取消操作，结果保留供 `lkit operation status`
与 `lkit operation list` 查询。CLI 连续 30 秒无法确认 daemon 存活时退出等待并
提示查询操作 ID，不修改操作状态；短暂重启期间继续等待。
`repair service` 仅允许取消排队请求；static／binary 的取消边界见下文。

操作记录位于 lkit 地盘 `run/operations/`，目录权限 `0700`、记录权限 `0600`，原子
写入并同步到磁盘，可以跨主机启动保留。记录只包含受支持的操作类型、安装根、状态、事务关联和结果说明，
repair 操作记录写入 schema v2，switch 写入 v3，restore 写入 v4，uninstall 写入 v5，网络确认／手工回滚写入 v6，reinit 写入 v7，install 写入 v8，migrate 写入 v9；不保存密码、环境变量或任意命令行。操作类型分别为 `repair_service`、
`repair_static`、`repair_binary`、`switch`、`restore`、`uninstall`、`network_confirm`、`network_rollback`、`reinit`、`install`、`migrate`，请求载荷按类型校验；未知类型、字段或不支持的
协议版本在入队前拒绝。操作类型与业务事务中的 `operation` 不必同名：
static／binary 对应 `repair` 事务，并分别校验 `static_backup`／`.lkb` 等恢复依据。

全屏观察页在网络待确认期间持续读取原操作记录。其他会话确认或 daemon 自动回滚后，
页面更新结果并关闭失效的确认层；进入恢复中时不再提供网络确认。结果页关闭返回最新
回执的退出码，仍在执行时关闭返回 `130`。确认请求仍由 daemon 在安装锁下重新校验。

## 串行执行与恢复

同一时间只运行一个修改工作流。领取顺序按操作 ID 排序；安装锁被占用或存在尚未
结束的事务时，排队请求等待。查询不等待安装锁；flare 与操作执行独立运行。
待确认网络事务不能被排队请求隐式确认，确认和回滚入口仍可处理该事务。

下载与健康检查使用异步任务，文件操作、备份及同步服务管理调用使用阻塞执行线程，
不能堵塞 daemon 的异步事件循环。操作记录锁只
保护短暂的领取和状态更新，不跨工作流持有。daemon 在发布 PID 和能力标记前安装退出信号处理器，启动准备期间收到停止信号也会
清理标记并退出。停止 daemon 时停止领取新操作，已经
运行的操作收尾后退出；进程崩溃则由新 daemon 根据持久化记录恢复。

daemon 重启后先处理遗留 `running`／`recovering` 操作，再领取新请求：

- 关联事务已提交：记录成功，不再次执行工作流；
- 关联事务已回滚或失败：记录失败；下载取消另须满足下文的持久化取消与清理条件；
- 关联事务未终结：记录恢复中，由事务恢复入口收尾，失败保留恢复依据；
- 没有事务关联，或关联事务文件不存在：记录中断，不把请求重新投入执行队列；
- 事务损坏、身份不匹配或状态不可读取：保留恢复中并报告原因，不猜测结果。

因此“先提交事务、后写操作结果”之间发生崩溃，也不会重复执行已提交的操作。
首次领取后、创建事务之前的崩溃可以导致请求中断，但不能导致静默重放。

## repair 请求与执行上下文

CLI／TUI 使用同一提交入口。请求绑定规范化安装根；static／binary 同时记录提交时的
活动版本与提交时安装状态的摘要。daemon 取得安装锁后重新验证安装状态、活动版本、
资产与服务归属；安装已被
替换、版本已切换或请求不再适用时终结为失败；安装状态摘要变化须重新提交请求。

| 操作类型 | 接受的业务参数 | 业务事务 |
|---|---|---|
| `repair_static` | 仓库选择、`official` | `repair`，静态快照 |
| `repair_binary` | 仓库选择 | `repair`，`.lkb` 与旧二进制等快照 |
| `repair_service` | 无仓库或资产参数 | `repair_service`，服务定义快照 |

仓库选择保留“不指定”“无值 `--repository` 选择镜像”“`--repository github`
选择官方 GitHub”“指定 BASE_URL”四种意图，不能把空值与未指定混为一谈。默认配置在领取后按命令定义的优先级解析；
解析出的资产来源、自定义前端选择、版本与校验身份在本次操作中保持一致，不能因
执行期间配置变化而切换来源。恢复只使用持久化事务和快照，不重新解析 latest。
凭据由 daemon 从受管配置读取，操作状态和进度不输出认证信息。

执行不读取原 CLI 的环境变量、工作目录或 `/dev/tty`。自定义前端获取失败时，操作
失败并提示 `--official`；CLI／TUI 可让用户确认后以显式 `official` 提交一个新的
操作 ID，daemon 不隐式回退，也不等待已经断开的前端回答。

binary repair 按安装记录的 systemd、OpenRC 或 SysVinit 后端执行停启与验证。
必须在修改前确认后端可管理该受管实例、导出可用且保护备份能够完成；不能管理时
失败，不要求用户在 daemon 执行期间手工停止进程，也不静默跳过健康检查。

提交入口验证运行中 daemon 支持对应操作类型及协议；能力不足时拒绝请求并提示
升级和重启 daemon。repair 的执行入口统一为结构化操作协议。

## 进度与取消

操作状态与工作流阶段分别记录。static／binary 的阶段包括校验、下载、准备、激活、
验证及回滚；binary 还包括停止服务。`running` 不等于“允许取消”，事务 `preparing`
也不等于下载阶段。进度包含当前阶段、可取消标识、下载字节数及总量（已知时）、结果
说明，并带单调递增的修订号。阶段切换和结果必须持久化；字节进度允许合并写入，
重连后可显示最近一次快照，不承诺逐条重放每个下载事件。进度写入不得将终态退回运行态。
结果保留业务退出码、错误说明和必要的备份／诊断引用；CLI 等待完成后沿用 repair 的
业务退出码，回滚失败不能被压成普通成功或取消。`operation status/list` 的退出码
表示查询是否成功，查询到失败操作仍正常返回该操作的失败状态。

`operation status <id>` 和 `operation list` 无需安装锁；CLI／TUI 连接同一操作 ID
读取快照，恢复展示不会重新提交或重新执行。关闭前端、SSH 断开和 CLI 的 Ctrl+C
仅结束等待。取消须使用 `operation cancel <id>` 或 TUI 明确的取消动作；两者调用
同一操作控制入口，不能通过发送信号终止整个 daemon。

| 当前阶段 | 取消行为 |
|---|---|
| `queued` | 与领取在同一记录锁下竞争，成功则持久化 `cancelled`，不执行工作流 |
| static／binary 的下载阶段 | 持久化取消请求，下载任务协作退出并清理，随后确认终态 |
| 准备、备份、停止、激活、验证或恢复阶段 | 明确拒绝取消，按事务提交或恢复 |
| `repair service` 已领取 | 明确拒绝取消 |
| 任意终态 | 不改变结果；重复取消已取消操作可返回现有结果 |

下载结束后，daemon 在同一控制同步边界检查取消请求并关闭取消窗口，随后才开始
备份、导出、刷新版本目录 `static.zip`、替换文件或停服务。取消先被接受则不能进入
这些动作；关闭窗口先完成则取消失败。客户端看到的旧进度不能绕过此检查。

接受下载取消不等于已经取消完成。取消意图和清理完成的依据必须持久化；只有下载
任务停止、临时资产清理完成、关联事务已终结且活动安装未改变，才记录 `cancelled`。
清理失败保留 `recovering` 及诊断信息，daemon 重启后继续清理，不重新下载。
不能只凭事务 `failed` 或一个取消标记推断取消成功；若无法证明取消发生在修改前，
按事务恢复并报告失败或中断，不伪造取消结果。

## repair 的恢复边界

static 修复保护静态目录、版本目录中的 `static.zip`（包含原先不存在的情况）和旧
安装状态。备份及关联先落盘，再修改这些对象；提交前崩溃或替换失败恢复三者的一致性。
不停止服务、不创建 `.lkb`、不恢复 Landscape data。自定义前端路径也必须记录实际
改动的对象，不能使用官方归档覆盖自定义页面。

binary 修复在停服务前完成 `.lkb` 校验、旧二进制和安装状态保存，以及服务状态和
必要宿主文件的快照。激活或验证失败使用这些依据恢复修复前现场；恢复失败保留
诊断材料和阻断状态，不因操作请求已经失败就允许下一项修改越过未完成的恢复。

资产快照带显式格式版本并校验对象归属，按对应版本的恢复规则读取。未知格式或
不完整的恢复依据必须阻断并报告，不能因缺少快照字段推断无需恢复。

两种资产修复均以业务事务的 `committed` 为成功依据。安装状态已经写入而事务仍未
提交的窗口，按事务阶段恢复，不能仅凭 state 摘要判定成功。事务提交后、操作结果
保存前崩溃则补写成功结果，不重新下载、备份、停启或替换文件。service 的 `finalizing`
前向完成规则只适用于服务定义修复，不能套用到资产修复。

## 验证要求

单元测试仅在临时地盘运行，注入执行器和事务状态，验证持久化、领取顺序、串行约束、
取消边界、事务关联及中断恢复。不能用最终返回成功代替执行次数断言。
CLI 与真实 daemon 的交互、前端断开、强杀 daemon、重启和结果查询在 CI fixture 中
验证。测试必须核对操作 ID、关联事务和执行结果，并核对服务管理子进程的父 PID
为 daemon PID。资产修复的验收场景及覆盖缺口见
[修复场景目录](../testing/scenarios/functional/repair.md)。
工作流单元测试验证业务逻辑；同一业务场景的端到端测试通过 daemon 操作入口
验证执行结果。排队取消、进度重连和中断不重放具有独立的操作生命周期场景。

## switch 请求与执行上下文

`switch` 使用操作 schema v3 和 `switch-v1.pid` 能力标记。参数为目标版本（精确 stable
版本或 `latest`）、仓库选择、`accept_service_change`、`allow_no_backup`，并绑定提交时
的活动版本与安装状态摘要。已解析目标版本独立持久化；事务关联必须匹配安装根、原版本
和解析出的目标版本。CLI／TUI 只提交和观察，daemon 直接调用切换工作流。

目标资源在事务临时根中下载、校验并应用自定义前端，现场缓存的可信目标版本复制复用。
下载取消完成清理后才报告 cancelled；进入 preparing 后不接受取消。旧安装状态、服务
定义和服务状态在停服务前保存，三个后端共用恢复规则。同版本校验成功可无切换事务；
已提交事务只补写操作结果，恢复失败保留阻断状态，不启动后续修改请求。
`update` 复用该操作类型、schema 与能力标记，提交的目标必须是前端已确认的精确 stable
版本；来源固定为确认时解析出的 provider kind 与 location，原活动版本和状态摘要也
来自该确认上下文。daemon 重新校验现场，可重新获取精确版本元数据，但不得重新查询
latest 或读取默认来源来改写请求。前端只读解析和等待确认不持有安装锁、不创建操作；
拒绝确认、同版本与降级均不入队。协议不接受任意命令行、环境或终端句柄。
详见 [`lkit switch`](../commands/switch.md) 与 [`lkit update`](../commands/update.md)。

## 备份恢复操作

`restore` 使用操作 schema v4 和 `restore-v2.pid` 能力标记。前端先验证目标备份并确认，
请求绑定安装根、当前版本和完整状态摘要，以及备份绝对路径、ID、目标版本和文件 SHA-256。
daemon 持锁后复核，变化时不创建事务。执行使用同一次读取并校验的字节，目标备份
复制到事务目录后独立于原文件。操作记录不包含备份中的配置、API token 或凭据。

restore 只允许取消排队操作，领取后不允许取消；Ctrl+C 退出观察不影响执行。
事务采用 schema v14，创建前持久化操作关联，保存独立的 `restore_confirmation`。
所有新恢复在目标健康检查通过后保存 pending state，进入 `awaiting_confirmation`；
原已提交安装状态保持不变。用户从备份中的网络重新连接并验证访问后，显式执行
`lkit network confirm`。`--yes` 只确认开始恢复，不代替网络确认。

`preparing` 中断清理临时内容并标记失败；`prepared`、停止、激活或验证阶段中断均
回滚旧 release、data 和服务状态，成功标记 `rolled_back`。待确认期间 daemon 重启
保留原期限；期限到达或主机重启自动回滚。确认经过
身份、健康和期限复核后持久化 `finalizing`，此决定在 daemon 或主机重启后继续提交，
不因期限到达而撤销。恢复失败保持未完成状态并阻止新操作。已提交事务只补写结果，
不重复执行 restore。读取旧 schema v9 事务时遵守其原有恢复规则，不推断新的确认窗口。

## 卸载操作

`uninstall` 使用 schema v5 和 `uninstall-v1.pid` 能力标记。请求绑定安装根、版本、完整
状态摘要、`allow_no_backup` 和 `keep_data`。daemon 持锁后复核身份与服务所有权，
直接执行卸载工作流。只允许取消排队操作，退出观察不停止卸载。

v10 卸载事务持久化 `uninstall_keep_data`；停止阶段之后中断时前向完成，保留相同清理
选项。恢复失败保持未完成并重试。完成后即使安装 state 已删除，也以保留的 committed
卸载事务核实成功并补写结果；不通过“根目录不存在”猜测成功。

## 网络确认与手工回滚

请求绑定安装根及首次接管、reinit 或 restore 的既有待确认事务 ID。daemon 在安装锁下优先处理此类请求，重新校验
事务身份、阶段及确认期限；它们可处理阻挡普通队列的待确认事务，不能越过安装锁。
新事务、没有确认窗口的事务和已终结事务不能接受旧请求。只有排队阶段允许取消。

确认以 `committed` 为成功依据，手工回滚以 `rolled_back` 为成功依据。关联事务仍为
`awaiting_network_confirmation` 时，执行失败记录失败，进程中断记录中断；不会重新
接受或重放确认。`finalizing` 和 `rolling_back` 由恢复入口继续收尾，操作保留恢复中，
终结后根据事务结果更新。自动回滚不需要用户操作请求。

## reinit 请求

reinit 使用结构化操作 schema v7，绑定规范化安装根、活动版本、安装状态摘要、
admin 用户名、新网络计划和是否允许缺少保护备份。密码通过操作 ID 对应的独立
`0600` 输入文件交接，不出现在状态 JSON、进度或日志中。输入文件在排队取消、
领取读取后及中断结果整理时删除；未完成入队留下的孤立输入在 daemon 调度前清理，
清理与提交共用队列锁。事务恢复不需要重放输入。

操作事务 schema v11，创建之前持久化操作关联。进入网络确认窗口后记录
`awaiting_confirmation` 并释放执行线程及安装锁；普通修改请求等待，绑定该事务的
网络确认／回滚可执行。操作成功以最终提交为依据，回滚对应失败退出码 `5`，
恢复尚未完成时保留恢复中并报告 `6`。

## install 请求

首次安装使用操作 schema v8，绑定规范化安装根、目标版本选择、仓库来源、管理员
用户名和可选网络计划。密码复用独立受限输入文件。目标为 latest 时 daemon 在领取
后解析一次并持久化具体版本，重启不再次解析。无安装状态时仍可领取首次安装请求；
安装锁、单实例检查和未完成事务恢复屏障同样适用。

业务事务使用 schema v12。下载和缓存复制位于事务暂存目录；取消或准备阶段中断
只清理暂存。准备完成后才发布资产、生成配置和注册服务。事务保存修改前目录及
后端身份，恢复先验证身份再恢复服务、DNS 和目录。提交依据包括相同事务 ID 的安装
状态，不能仅凭相同版本将另一次安装误认为本次成功。

## migrate 请求

迁移使用操作 schema v9 和业务事务 schema v13。请求绑定规范化源与目标目录、源目录
设备／inode、旧进程 PID／启动时刻及二进制和命令行摘要、导出版本与旧 systemd unit。
确认前只读；备份、服务停止和安装状态写入均由 daemon 执行。排队可取消，领取后前端
只观察。旧前台进程需要人工停止时，阶段为 `waiting_for_source_stop`，进度说明包含 PID；
超时不继续激活目标。

旧 unit 的恢复信息先于 stop、disable、移动或 mask 持久化。恢复失败保留非终态，
再次恢复可以识别已经放回原位的 unit，不要求备份文件仍在原位置。状态已提交但
操作结果丢失时，通过事务 ID 补全结果，不重放迁移。

## 操作语言

`operations-v3` 能力支持可选的 `language: en|zh`。请求保存前端最终选择的语言，daemon
仅在执行该操作的线程中临时应用，完成后恢复原语言；不传递 `LANG`、`LKIT_LANG` 等
会话环境。旧记录没有此字段时使用 daemon 默认语言。

## 执行步骤与诊断输出

操作回执的 `message` 表示当前结果。网络确认完成、自动回滚完成或恢复重试最终结束后，
说明与状态、退出码一致，不保留待确认或尚未恢复的操作指引；恢复失败且未终结时保留失败原因。

每个操作可有独立的 `run/operations/<id>.events` 步骤记录，权限 `0600`，原子更新，
最多保留最近 128 条。记录包含递增序号、UTC 时间及预定义步骤／阶段／状态，不包含
凭据、配置正文、仓库 URL、请求参数或子进程原始输出。日志失败不改变业务结果。
旧 daemon 没有步骤文件时，前端仍展示原有阶段与结果，不要求重新安装服务。

TUI 默认读取步骤时间线；安装依次展示环境检查、版本解析、缓存校验、后端下载校验、
解压、静态资源下载解压、前端准备、保存恢复现场、生成配置、发布版本、宿主网络接管、
服务注册启动、启动健康检查、稳定观察、提交或等待网络确认。步骤表示当前正在尝试的
动作，成功与否以最终操作回执为准。

CLI `--debug` 在 stderr 显示步骤时间线和操作 ID、事务 ID、状态、阶段、revision、
下载字节数及退出码；普通输出保持简洁。`lkit operation status <id> --debug` 同样
显示已保存步骤，stdout 仍为操作 JSON。调试模式只影响前端观察，不修改 daemon 环境，
不要求重启 daemon，也不转发任意命令行或敏感输出。
